# Architecture

## 1. Purpose
CPG Analytics Copilot answers business questions and runs structured investigations over CPG sales, inventory, promotion, pricing and competitor data. Its central rule: **the LLM interprets and narrates; deterministic, governed code calculates.**

## 2. System context
```
Browser (React/Vite)
   |  HTTPS + Bearer JWT
   v
FastAPI (backend/app)
   |-- Auth / RBAC / row-level scope        security.py
   |-- Agent (Groq tool loop | offline)     agent.py, llm.py, nlu.py
   |-- Governed tool registry               tools.py
   |      \-- Analytics engine              analytics/{core,performance,commercial,ops,pulse}.py
   |             \-- Semantic layer         semantic.py
   |-- Investigation engine                 investigation.py
   |-- Institutional memory                 memory.py
   |-- Governance, audit, telemetry         governance.py, telemetry.py
   v
Two databases
   - Analytics DB (SQLAlchemy): SQLite by default `data/cpg.db`; Azure SQL via ANALYTICS_DB_URL
   - State DB (sqlite3): `data/state.db` (chats, evidence, investigations, audit, telemetry ...)
External: Groq API (optional), webhook for workflow tasks (optional), OIDC JWKS endpoint (optional)
```

## 3. Layers and responsibilities
| Layer | Module(s) | Responsibility |
|---|---|---|
| Presentation | `frontend/src` | Chat, Business Pulse, Investigations, Knowledge Base, Governance, Operations, shared read-only view |
| API | `routes.py`, `main.py` | REST endpoints, request-ID middleware, safe error handlers, optional static serving of the built UI |
| Identity & access | `security.py` | Local JWT login or OIDC bearer validation; roles → allowed tools and features; per-user data scope |
| Orchestration | `agent.py` | Conversation lifecycle, context retention, Groq tool loop, offline planner, evidence creation, grounding check, suggestions |
| Tool governance | `tools.py` | Allow-list, JSON-schema validation, argument coercion, scope enforcement, metadata (SQL, lineage, freshness, DQ), telemetry |
| Analytics | `analytics/*` | Period logic, SQL builder, comparisons, decomposition, promo/stockout/price/forecast models, radar |
| Semantic layer | `semantic.py` | Certified metrics, dimensions, hierarchies |
| Investigation | `investigation.py` | Plan → hypotheses → tests → challenge → confidence → summary → graph → replay |
| Memory | `memory.py` | Issue memory, similarity, hypothesis recall, outcome monitoring |
| Governance | `governance.py` | Metric catalog versions, audit writes |
| Observability | `logging_setup.py`, `telemetry.py` | JSON logs with request IDs, LLM/tool call telemetry |

## 4. Key flows

### 4.1 Chat question
1. `POST /api/chat` → `agent.chat`: load/create conversation, load last 8 messages and saved context.
2. If a Groq key exists: build system prompt (rules, metrics, dimension values, user scope, context) and send only role-allowed, keyword-relevant tool schemas. Loop up to `MAX_TOOL_ROUNDS` (6).
3. Each tool call → `tools.execute`: role check → coerce/validate args → `Ctx(scope)` → analytics function → attach metadata → record telemetry.
4. Successful results are stored in `evidence` (label `E{n}` per conversation) and a compact version is fed back to the model.
5. Final answer is post-processed: citations ensured, grounding check run, suggestions generated, context saved, audit row written.
6. If Groq is missing or fails twice, `offline_plan` maps the question to one tool with the same governed path.

### 4.2 Investigation
`investigation.start` runs: observation gap → timing baseline → 12 hypothesis tests (each calls governed tools, storing evidence) → untestable hypotheses → scoring/ranking → challenge → confidence → claims → recommendations → narrative (LLM optional) → graph + replay → similar-issue lookup → persist. See `agent_design.md` for the scoring rules.

### 4.3 Proactive radar
`detect_business_issues` scans anomalies by dimension and region×category, stockout spikes, ended promotions, price rises and competitor spikes; clusters related signals; scores materiality; persists per scope hash in `radar_issues`; optionally auto-creates investigations.

## 5. Trust boundaries
- The browser is untrusted: every endpoint re-checks token, role feature and (for investigations) scope visibility.
- The LLM is untrusted: it can only call allow-listed tools with validated arguments; it cannot reach the database, the file system or other users' data.
- SQL is never generated by the model: identifiers come from allow-lists, values are bind parameters.
- Shared links expose a sanitised read-only snapshot (summary, hypotheses, charts) with expiry and revocation.

## 6. Deployment shapes
- **Local (default):** SQLite for both databases, one uvicorn process, optional Vite dev server.
- **Single process:** `npm run build`; backend serves `frontend/dist`.
- **Enterprise (not verified here):** `ANALYTICS_DB_URL` to Azure SQL, `AUTH_MODE=oidc`, `WORKFLOW_WEBHOOK_URL`, reverse proxy + TLS. The state DB remains SQLite and would need replacing for multi-instance deployment.

## 7. Known constraints
- Single-node state store (SQLite) and in-process caches; not horizontally scalable as shipped.
- Weekly grain only; weeks are assigned to periods by week-start date.
- Groq calls are synchronous inside the request.
