# Data Model

Two stores: the **analytics database** (business facts, read-only for the app) and the **state database** (application data). Defaults are SQLite files in `backend/data/`.

## 1. Analytics database (`cpg.db`, or Azure SQL via `ANALYTICS_DB_URL`)
Created by `seed.py` only if `fact_sales` is absent. To use real data, supply tables/views with these names and columns. Dates are ISO strings (`YYYY-MM-DD`) in SQLite; the SQL uses only standard constructs (SUM, CASE, COUNT DISTINCT, IN, BETWEEN, GROUP BY) so it ports to other dialects.

### fact_sales (grain: week × product × region × channel × segment)
| Column | Notes |
|---|---|
| week_start | Monday of the week (period membership is by this date) |
| month, quarter, year | Derived from week_start (`2026-08`, `2026-Q3`, 2026) |
| product_name, category, subcategory, brand | Denormalised product hierarchy: category > brand > product |
| region, channel, segment | Dimensions |
| units, list_price, gross_revenue, discount_pct, revenue, cogs | `gross_revenue` at list price; `revenue` net of discount; `discount_pct` may be NULL (flagged by DQ) |
| promo_flag | 1 when the row sold on promotion |

### fact_inventory (week × product × region)
`week_start, product_name, category, brand, region, stock_on_hand, stockout_days (0-7)`. No channel/segment: queries scoped by channel/segment are denied for inventory (fails closed).

### fact_promotions
`promo_id, product_name, category, region ('All' or name), channel ('All' or name), start_week, end_week (week_start of first/last promo week), discount_pct, mechanic, siblings` (comma-separated substitute products used for cannibalisation).

### fact_competitor (external)
`week_start, category, price_index, promo_intensity (0-1), source`. Only some categories have data; missing categories are reported as unavailable evidence.

### fact_cohorts
`cohort_month, segment, months_since, cohort_size, active_customers`.

### data_sources
`source_name, table_name, last_refreshed, cadence_hours, system, owner` — drives freshness/stale flags.

### dq_results (generated by `run_dq_checks`)
`check_name, severity, status, detail, entity (JSON), week_from, week_to, affected_rows, table_name, checked_at`. Checks: grain completeness, null discount on promoted rows, negative values, duplicates, freshness per source.

### Semantic layer (code: `semantic.py`)
Dimensions: sales — category, brand, product_name, region, channel, segment; inventory — category, brand, product_name, region; time — week_start, month, quarter, year. Hierarchies: product (category>brand>product_name), geography, channel, customer.

Base additive measures: sales — revenue, units, cogs, gross_revenue, promo_revenue, promo_units; inventory — stockout_days, pr_weeks (product-region-weeks), stock_units. Metrics computed from them:
| Metric | Definition |
|---|---|
| revenue | SUM(revenue) |
| units | SUM(units) |
| avg_price | revenue / units |
| gross_margin_pct | (revenue − cogs) / revenue × 100 |
| promo_share | promo revenue / revenue × 100 |
| discount_depth | (1 − revenue / gross_revenue) × 100 |
| stockout_rate | stockout_days / (7 × product-region-weeks) × 100 |
| stockout_days | SUM(stockout_days) |
Ratios are computed after aggregation (never averaged), and additive metrics support contribution analysis.

### Period handling
Weeks belong to a period by `week_start`. Calendar words are relative to the latest data date (`as_of` week + 6 days). When the comparison period has a different number of weeks, comparison values are scaled to the current period's week count and a warning is attached.

### Synthetic dataset (seed)
104 weeks ending on the last completed week; 12 products, 5 regions, 4 channels, 3 segments (~75k sales rows); 7 promotions; weekly competitor signals for 3 categories; 18 monthly cohorts. Seeded storylines and planted DQ issues are listed in `seed.py` and the README.

## 2. State database (`state.db`, SQLite)
| Table | Purpose / key columns |
|---|---|
| users | id, username, display_name, role, scope_json (e.g. `{"region":["North"]}`), pw_hash, salt (PBKDF2) |
| conversations | id, user_id, title, archived, context_json, created_at, updated_at |
| messages | id, conversation_id, role, content, payload_json (evidence blocks, suggestions, grounding, tools), created_at |
| evidence | id, owner_type (`conversation`/`investigation`), owner_id, label (`E1`…), message_id, tool, args_json, result_json (full result incl. SQL/lineage), created_at |
| investigations | id, user_id, conversation_id, title, observation, status, priority, owner, due_date, source (`user`/`radar`), issue_id, data_json (spec, scope, gap, plan, hypotheses, challenge, confidence, summary, graph, replay, similar, recall), timestamps |
| comments | id, investigation_id, user_id, body, mentions_json, created_at |
| notifications | id, user_id, kind, body, link, read, created_at |
| shares | token, investigation_id, created_by, permission, expires_at, revoked |
| issue_memory | id, investigation_id (NULL for seeded), title, signature_json, text, hypotheses_json, root_cause, outcome_json, source, occurred_on |
| outcomes | id, investigation_id, action, result, metric_before/after, notes, created_by |
| actions | id, investigation_id, title, description, owner, due_date, status, created_by, completed_at |
| radar_issues | id (`issue_id:scope_hash`), data_json, score, status (`new`/`investigating`/`dismissed`), investigation_id, scan_id |

| audit | id, ts, request_id, user_id, role, action, detail_json |

| workflow_tasks | id, investigation_id, title, system, external_ref, status, payload_json |

### Relationships and lifecycle
```
conversations 1─* messages
conversations 1─* evidence (owner_type=conversation)
conversations 1─* investigations (created from chat)
investigations 1─* evidence (owner_type=investigation), comments, actions, outcomes, shares, workflow_tasks
investigations 1─0..1 issue_memory (created on conclude/close)
radar_issues 0..1─1 investigations
```
Deleting a conversation removes its messages, evidence and the investigations it created (with their children). Deleting an investigation also detaches its radar issue (back to `new`) and removes its memory entry.

### Visibility rule
A user may view an investigation if they have no scope, or every dimension in their scope is covered by (a subset of) the scope under which the investigation was created. This prevents a scoped user seeing data computed for a wider scope.
